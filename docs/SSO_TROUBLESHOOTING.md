# LDAP SSO Troubleshooting

This guide records the LDAP, Keycloak, Expo, and FastAPI issues encountered while enabling SahAI SSO.

## Architecture

```text
SahAI frontend -> Keycloak -> OpenLDAP
       |
       v
SahAI FastAPI API validates the Keycloak access token
```

The frontend does not receive or store an LDAP password. Keycloak authenticates the user against LDAP and returns an OIDC access token. FastAPI verifies that token and maps the user's Keycloak groups or roles to a SahAI role.

## Incident Timeline

The connection errors occurred in stages. This distinction is useful when diagnosing the app:

1. The backend process was not running, so port `5000` was closed. The frontend correctly could not reach FastAPI.
2. The backend was started, but an older Uvicorn/dev supervisor continued serving the old process. Restarting only one child process did not replace the listener.
3. Chrome then reached `/auth/me`, but the old worker returned incomplete CORS headers. Chrome reported this as a network failure even though FastAPI was reachable.
4. After the clean backend restart, `/auth/me` returned `401 Not authenticated` without a token. That is a healthy response and proves the API is reachable.
5. Once the network path worked, the real SSO-specific errors appeared: invalid redirect URI, invalid scope, missing PKCE verifier, and missing RSA cryptography support.

When the frontend displays `Cannot reach the SahAI server`, check the port and the browser console first. Do not assume every occurrence means the backend is stopped: a CORS rejection also makes browser `fetch()` reject before the frontend receives an HTTP status.

## Errors and Fixes

### 1. OIDC discovery stack trace: `fetchDiscoveryAsync` / `resolveDiscoveryAsync`

**Cause:** Expo AuthSession could not reach the configured Keycloak realm. In this setup the Docker Desktop Linux engine was stopped, so the Keycloak container and port `8080` were unavailable.

**Fix:** Start Docker Desktop, wait for its engine to become ready, then start the identity services:

```powershell
docker compose --env-file .env -f docker-compose.keycloak.yml up -d
```

Verify the realm endpoint:

```powershell
curl.exe -I http://localhost:8080/realms/sahai/.well-known/openid-configuration
```

It should return `200`. The frontend now constructs Keycloak's standard realm endpoints directly, so a stopped Keycloak server no longer crashes the login screen, but SSO still requires Keycloak and OpenLDAP to be running.

### 2. `Cannot start SahAI: Frontend dependencies missing`

**Cause:** `frontend/node_modules` did not exist.

**Fix:** Install frontend dependencies from the `frontend` directory:

```powershell
cd frontend
npm.cmd install
```

On this Windows setup, `npm` was blocked because PowerShell tried to run `npm.ps1`. `npm.cmd` bypasses that execution-policy issue.

### 3. `npm is not on PATH`

**Cause:** The PowerShell npm wrapper was unavailable or blocked, even though Node.js was installed.

**Fix:** Confirm Node.js is installed and use the command shim:

```powershell
Get-Command node,npm.cmd,npx.cmd
npm.cmd install
```

### 4. `cd frontend` cannot find `frontend\frontend`

**Cause:** The shell was already inside the `frontend` directory.

**Fix:** Run the npm command directly:

```powershell
npm.cmd run web -- --clear --port 8081
```

Use `cd ..` only when returning to the repository root.

### 5. `Port 8081 is being used by another process`

**Cause:** An older Expo/Metro process was still listening on port `8081`.

**Fix:** Find and stop the listener, then restart Expo:

```powershell
$connections = Get-NetTCPConnection -State Listen -LocalPort 8081
$connections.OwningProcess | Sort-Object -Unique | ForEach-Object {
  Stop-Process -Id $_ -Force
}

cd frontend
npm.cmd run web -- --clear --port 8081
```

### 6. Backend would not start because `httpx` was missing

**Cause:** `backend/services/weather.py` imports `httpx`, but it was not listed in `requirements.txt`.

**Fix:** Add/install the dependency:

```powershell
python -m pip install "httpx>=0.27.0"
```

`requirements.txt` now declares `httpx>=0.27.0`.

### 7. `Invalid parameter: redirect_uri`

**Cause:** The redirect URI generated by Expo was not registered in the Keycloak client.

**Fix:** In realm `sahai`, client `sahai-api`, configure:

```text
Client authentication: Off
Standard flow: On
Valid redirect URI: http://localhost:8081/login
Web origin: http://localhost:8081
```

The URI must match exactly. Remove obsolete callback values such as `/oauth/callback` when they are not used by the current frontend.

### 8. `invalid_scope` for `groups`

**Cause:** The frontend requested the OAuth scope `groups`, but that client scope was not defined in Keycloak.

**Fix:** The frontend now requests only standard scopes:

```text
openid profile email
```

Configure a Keycloak groups mapper/client scope separately if group claims are required. The backend also accepts `realm_access.roles`.

### 9. Expo showed `Unmatched Route` at `/oauth/callback`

**Cause:** Expo Router had no route named `/oauth/callback`.

**Fix:** The frontend now uses the existing login route as the OAuth redirect:

```text
http://localhost:8081/login
```

`WebBrowser.maybeCompleteAuthSession()` is called so the browser callback completes in the originating tab.

### 10. `PKCE code verifier not specified`

**Cause:** The PKCE verifier was initially passed to Expo's token exchange using the wrong property.

**Fix:** The token exchange sends it as:

```js
extraParams: { code_verifier: request.codeVerifier }
```

Always start a new authorization attempt after changing PKCE code. Old authorization codes expire or can only be used once.

### 11. `RSAAlgorithm` was unavailable

Error:

```text
AttributeError: module 'jwt.algorithms' has no attribute 'RSAAlgorithm'
```

**Cause:** PyJWT was installed without its RSA cryptography dependency.

**Fix:** Add/install:

```powershell
python -m pip install "cryptography>=42.0.0"
```

`requirements.txt` now declares `cryptography>=42.0.0`.

### 12. Backend unavailable: `Cannot reach the SahAI server`

Browser message:

```text
Cannot reach the SahAI server. Check that the backend is running.
```

**First cause:** The backend was not running, so nothing was listening on port `5000`. This can happen after closing the terminal, after a failed startup, or when the `dev.py` supervisor exits.

Check both services:

```powershell
curl.exe -I http://127.0.0.1:5000/docs
curl.exe -I http://localhost:8081
```

If the API check fails, start the backend from the repository root:

```powershell
$env:SAHAI_AUTH_MODE="oidc"
$env:KEYCLOAK_ISSUER="http://localhost:8080/realms/sahai"
$env:KEYCLOAK_AUDIENCE="sahai-api"
python -m uvicorn backend.app:app --host 0.0.0.0 --port 5000
```

Keep that terminal open. If an old Uvicorn process still owns port `5000`, stop the complete process tree before starting a new one.

**Second cause:** Once the backend was running, Chrome sometimes still showed this message because of localhost networking or CORS. The frontend's `fetch()` rejects both transport failures and browser-blocked CORS responses, so the message is deliberately supplemented with the failing URL during development.

**Cause:** Chrome and Expo sometimes resolved `localhost` differently from the backend binding, especially when IPv6 (`::1`) was selected.

**Fix:** Web frontend API configuration now explicitly uses:

```text
EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:5000
```

The backend should be started with:

```powershell
python -m uvicorn backend.app:app --host 0.0.0.0 --port 5000
```

The browser frontend uses the explicit IPv4 URL:

```text
EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:5000
```

This avoids Chrome resolving `localhost` to IPv6 while Uvicorn is listening on IPv4.

### 13. CORS error on `/auth/me`

Browser error:

```text
Access to fetch ... has been blocked by CORS policy
```

**Cause:** A stale backend worker was serving the old CORS configuration, and Expo can use a different local port when `8081` is occupied.

**Fix:** The FastAPI development CORS policy allows wildcard origins without cookies. SahAI sends bearer tokens through the `Authorization` header, not browser cookies:

```python
allow_origins=["*"]
allow_credentials=False
```

Stop stale Uvicorn/dev supervisor processes before restarting the backend. A normal unauthenticated request to `/auth/me` returning `401 Not authenticated` proves the API is reachable; it is not a network failure.

The follow-on error after a successful connection may be:

```text
{"detail":"Invalid Keycloak token."}
```

That means the request reached FastAPI and the token was rejected. Check Keycloak issuer, audience, RS256 signing keys, PKCE exchange, and role claims. It is different from a closed port or a browser CORS failure.

### 14. Authentication returned to the previous user after logout

**Cause:** SahAI cleared its local token, but Keycloak still had an active browser SSO session.

**Fix:** The authorization request now includes:

```text
prompt=login
```

This forces Keycloak to show the login/account selection screen again. For a complete identity-provider logout, also use Keycloak's logout action or choose a different account in the Keycloak screen.

### 15. Users could not be created in Keycloak

Keycloak logged:

```text
No Such Object
remaining name 'ou=users,dc=sahai,dc=local'
```

**Cause:** The LDAP base OU configured in Keycloak did not exist.

**Fix:** Create the OU in OpenLDAP:

```powershell
$ldif = @"
dn: ou=users,dc=sahai,dc=local
objectClass: organizationalUnit
ou: users
"@

$ldif | docker exec -i sahai-openldap ldapadd `
  -x `
  -D "cn=admin,dc=sahai,dc=local" `
  -w "change-me-ldap-admin"
```

Then test the Keycloak LDAP provider connection and authentication. Use `WRITABLE` mode if Keycloak should create LDAP users; use `READ_ONLY` if users must be created directly in LDAP.

### 16. Existing SQLite users were not visible in LDAP

**Cause:** SQLite and LDAP are separate identity stores. The project database did not contain users at the time checked, and SQLite PBKDF2 hashes cannot be copied directly into LDAP.

**Fix:** Create LDAP users separately, using the same `member_id` as the LDAP `uid`. Assign exactly one role group:

```text
sahai-members
sahai-treasurers
sahai-admins
```

If migrating real SQLite users, export only `member_id`, name, and role. Create new LDAP passwords or temporary reset passwords. Never copy SQLite `password_hash` values into LDAP.

## Correct Startup Procedure

From the repository root:

```powershell
$env:SAHAI_AUTH_MODE="oidc"
$env:KEYCLOAK_ISSUER="http://localhost:8080/realms/sahai"
$env:KEYCLOAK_AUDIENCE="sahai-api"
python dev.py --host 0.0.0.0
```

The frontend environment file should contain:

```text
EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:5000
EXPO_PUBLIC_AUTH_MODE=oidc
EXPO_PUBLIC_KEYCLOAK_ISSUER=http://localhost:8080/realms/sahai
EXPO_PUBLIC_KEYCLOAK_CLIENT_ID=sahai-api
```

Open:

```text
http://localhost:8081/login
```

Keep the terminal running. Closing the terminal stops the backend and frontend.

## Quick Health Checks

```powershell
curl.exe -I http://127.0.0.1:5000/docs
curl.exe -I http://localhost:8081
curl.exe -I http://localhost:8080/realms/sahai/.well-known/openid-configuration
```

Expected status for all three services is `200`.

A request without a token should return `401`, which confirms the backend is alive:

```powershell
curl.exe -i http://127.0.0.1:5000/auth/me
```

## Production Notes

- Replace all development passwords.
- Use HTTPS for Keycloak, FastAPI, and the frontend.
- Keep LDAP private and reachable only by Keycloak.
- Use a secret manager for `SAHAI_SECRET_KEY`.
- Register only real frontend redirect URIs in Keycloak.
- Use a persistent production database instead of SQLite for multiple backend instances.
